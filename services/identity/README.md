## 📖 API Reference & Testing Guide

This API strictly adheres to a standard JSON envelope response pattern:
- **Success (`200 OK`)**: `{ "success": true, "message": "...", "data": { ... } }`
- **Error (`400/401`)**: `{ "success": false, "message": "...", "errorCode": "...", "traceId": "..." }`

### 1. Health Check
Verifies the service is alive and running.

- **URL:** `GET /health/identity`
- **Auth Required:** No
- **Test Command:**
  ```bash
  curl -s http://localhost:5001/health/identity
  ```

### 2. User Login
Authenticates a user and sets an `HttpOnly` secure cookie (`sc_token`) for subsequent requests. This cookie contains an RS256-signed JWT.

- **URL:** `POST /api/identity/v1/auth/login`
- **Auth Required:** No
- **Payload:**
  ```json
  {
    "email": "super@shiftcore.local",
    "password": "Password123!"
  }
  ```
- **Test Command:** (Saves the cookie to a local `cookies.txt` file)
  ```bash
  curl -c cookies.txt -s -X POST http://localhost:5001/api/identity/v1/auth/login \
       -H "Content-Type: application/json" \
       -d '{"email": "super@shiftcore.local", "password": "Password123!"}'
  ```

### 3. Get Current User Profile (`/me`)
Validates the secure cookie and retrieves the current user's profile and permissions directly from the JWT claims (Stateless).

- **URL:** `GET /api/identity/v1/auth/me`
- **Auth Required:** Yes (Cookie)
- **Test Command:** (Reads from `cookies.txt`)
  ```bash
  curl -b cookies.txt -s http://localhost:5001/api/identity/v1/auth/me
  ```

### 4. Logout
Invalidates the current session and instructs the browser to delete the `sc_token` cookie.

- **URL:** `POST /api/identity/v1/auth/logout`
- **Auth Required:** Yes (Cookie)
- **Test Command:**
  ```bash
  curl -b cookies.txt -s -X POST http://localhost:5001/api/identity/v1/auth/logout
  ```

## 🤝 For Other Service Owners (Core, AI)

The Identity API generates standard **RS256 JWT tokens** and injects them securely into an `HttpOnly` cookie named `sc_token`.

### How to authenticate requests in your service:
1. **Stateless Validation:** You do **not** need to call the Identity API to validate a user.
2. **Extract Cookie:** Read the `sc_token` cookie from the incoming HTTP request.
3. **Verify Signature:** Parse the JWT locally in your service using the **Public Key** (`jwt_public.pem`).
4. **Verify Claims:** Check the required claims (`iss`, `aud`, `exp`) per the `contracts/auth-claims.md` contract.
5. **Trust Context:** Extract user context (`sub`, `email`, `role`, `teamId`) from the JWT claims and trust them.

### Local Development Keys
Your service must mount the `.secrets` directory (generated by `scripts/generate-jwt-keys.sh` in the root) to access the `jwt_public.pem`. This is already configured in the root `docker-compose.yml`.
